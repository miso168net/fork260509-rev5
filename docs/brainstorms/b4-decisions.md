## Q6・事件帳 summary 單筆上限

**裁決：上限 300 字、禁含換行；執行條款＝併入 Lint03。**

- **上半（數值）**：回歸設計預測值「一刀約 300 字」。rev4 零限制的結果是單筆最長 2,498 字、中位 953 字（＝預測值 3.2 倍），且為 events.jsonl 膨脹至 35,905 tokens 的主因之一。
- **下半（執行條款）**：★此半題原為全檔未指定——§3.2 條 11 只寫「加進事件 schema 並指定執行條款」，附錄 A 的名冊無對應條目。裁決為**併入 Lint03**（事件帳 schema 驗證），理由：summary 長度本質即「欄位形」的一部分，與 `merge` 必為 40-hex、`findings` 四鍵守恆律同層級；`_check_event` 已逐欄驗形，加一條長度斷言是最小改動。
- **操作化**：jsonl 單列結構下「行數型上限」落實為「禁含換行 ＋ 字元數上限」（NOTES 那種真行數預算套不進 JSON 字串欄）。
- **連動面**：條款總數不變 → 不觸發 Lint22 範圍字串連動。同刀改對應字面自測（B4 丙）。
- **溢出去處**：細節 → `notes` 選填欄／報告檔／LESSONS。★`notes` 刻意不設限——創世事件的 `notes` 要承載 `lint-roster:` 固定前綴（一行逗號分隔全部條款名）。
- **★一次性**：事件帳「既有列不可改」，本值創世後定死、不能回頭改舊列。

## Q7・pre-commit 全鏈時間門檻

**裁決：20 秒 WARN ＋ 45 秒 ERROR 兩級。**

- **基準點**：rev4 從 46.4s 劣化至 104.6s（2.2 倍）全程零警報；事後 O(1) 化修復至 15.7s（WSL2 實測）。本機 Day 1 實測 0.5s（鏈提前短路，屬下限非健康值）。
- **兩級的作用分離**：20s WARN 給劣化趨勢訊號但放行，不因一次環境抖動卡住工作流；45s ERROR 硬擋——**rev4 的劣化起點 46.4s 恰好被擋下**，不會重演「漂到 104.6s 才靠人感覺發現」。
- **跨平台**：門檻須同時容 macOS APFS 與 WSL2 drvfs（同工具實測差一個量級：19s vs 1.27s）。45s 對 rev4 在 WSL2 上的健康值 15.7s 有 3 倍餘裕。
- **調整程序**：走 ADR（§0.3 準則 5 慣例）。門檻做成機器斷言、實作點隨 B4 丁。

## Q10・活書單節配額

**裁決：十二格全數不動**（§9=5、§11=3、§6=120、§7=60、§10=40…）。

### 先澄清的機制事實

判定式是 `count > quota`——**嚴格大於才報，等於配額不報**。所以「頂格」不等於「已在警告」，而是「再多一行就叫」；且單節超額只是 **WARN 放行**，硬擋的只有全檔 700 行／25,000 tokens。

### §9／§11（指標節）

實測 rev4 as-built：§9 僅 2 行、§11 僅 1 行，節內明寫「本節不承載內容」。**空殼是設計如此，不是 rev4 的偶然**——故 §3.3「十二格零漂移可原樣照搬」是對的讀法，§4.5.3 常數 8「rev5 應重議」的前提（空殼＝實情特化）不成立。

配額在這兩節的作用是**絆線**而非上限壓力：維持 5／3 ＝ 多寫一行就叫、訊號最早到；放寬 ＝ 絆線變鈍；取消 ＝ 絆線拆掉（永不叫）。

### §6／§7（內容節）——本輪新查

| 節 | 用量 | 平均行寬 | 最長行 | 括號嵌套 |
|---|---|---|---|---|
| §6 Runtime | 120/120（100%） | 87 字 | **272 字** | **157** |
| §7 部署 | 60/60（100%） | 66 字 | 86 字 | 45 |
| §10 品質要求 | **39/40（97.5%）** | 61 字 | — | 20 |
| §8 橫切概念 | 21/90（23%） | **212 字** | — | 40 |

**關鍵反直覺**：rev4 全檔只用 373/700 行、14,216/25,000 tokens（53%／57%）——**檔案層閒置近一半餘裕，卻是單節配額在逼壓縮**。§6 那條 272 字的行與 157 個嵌套括號即是證據。

但反方證據決定了裁決：被壓最兇的 §7 reaper 那條（佔 9 行）寫的是 CLI 旗標分派、DB role 授權明細、心跳推送分組——**這些本就該住 RUNBOOK／ADR，不是活書 §7 的料**。所以壓縮痕跡是「內容放錯家」的訊號，而非「配額太緊」，正是 §3.3「快變事實去處」欄的設計用意。

加上 rev5 是**重寫而非累積**（通常比二十刀疊出來的文字緊），且 WARN 不擋 commit——真不夠用時第一次撞 WARN 就會知道，那時手上有實際內容可判斷「該搬還是該調」，比現在猜一個數字好。

### ★兩件啟動書未記的發現（已入本檔備查）

1. **§10 也在天花板下一行**（39/40），啟動書 §3.3 L300 只點名 §6／§7——且該處標題寫「兩則實測提醒」實際只給一則。
2. **行數型配額對散文節可被繞過**：§8 用 21 行（僅 23% 配額）裝了比 §7 更多的字（21×212 ≈ 4,452 vs 60×66 ≈ 3,960）。不是破口——全檔 25,000 token 硬閘仍抓得到——但代表單節配額量錯了東西。**已評估「改 token 型單節配額」並否決**：十二個新數值無 rev4 實戰基準可錨、只能拍腦袋，而全檔 token 閘已能攔寬度規避，邊際效益有限。

## Q13・review findings.total 雙源對賬

**裁決：Day 1 補實作。**

- **現況已親驗**：`grep -rn 'findings_total' tools/ .githooks/ .githooks-submodule/` → **零命中**，啟動書「as-built 從未實作」的宣稱屬實。現有的只是單源——事件內部四鍵守恆律（`fixed + len(to_backlog) + len(wontfix_adr) == total`）已在 Lint03。
- **★實作成本比啟動書描述的低**（本輪實查）：`parse_front_matter()` 已存在且被 ADR 用了六處；`lint_review_existence`（Lint05）已在逐筆讀 report 檔路徑並驗存在性（自動補 `docs/` 前綴）。缺的只是「讀進來比一個數字」。
- **接線位置**：Lint05 現有 report 存在性檢查之後，讀報告 front-matter 取 `findings_total`、與事件 `findings.total` 比對，不符即 ERROR。
- **★順帶定下 review 報告 front-matter 規格**（啟動書原缺——ADR 有規格、review 報告沒有）：
  - 唯一必填欄 `findings_total`，型別＝非負整數
  - 沿用現有解析器吃得下的 YAML 子集（帶引號或裸 scalar、flow list、空 list；**不支援區塊式 list**）
  - 缺 front-matter 或缺該欄即 ERROR
- **依據**：符合 §0.3 準則 1（治理能力零空窗，不必立延後 ADR）與準則 7（對賬全機器化或顯式列冊）。
- **代價**：寫第一份 review 報告時必須帶 front-matter，否則被擋。
