- **L-062**｜**在 drvfs（WSL2 的 /mnt/*，9p）上，治理工具的耗時幾乎全是「單次 I/O 延遲 × 存取次數」的稅，不是條款邏輯；憑直覺列的優化清單會全數落空**：B-130 條目原列三個處置面（剖析 `docs-sync lint` 慢條款／`docs-sync test` 案分層／`fork-delta-lint` 成長面）皆假設成本在邏輯，2026-08-25 剖析後**全數證偽**——`docs-sync lint`（cProfile 19.3s）檔案系統原語佔 **64%**（`open` 1407 次／`stat` 1428 次），唯一顯著的邏輯成本 `scan_id_namespace` 僅 **7%**；`fork-delta-lint`（14.3s）`select.poll` 佔 **99%**（50 個 `git show` 逐次序列等待），檔案 I/O 僅 0.167s。★**量化**（受控微基準、同一批 269 檔 stat+read）：drvfs **2845ms** vs 原生 ext4 **4.8ms** ＝ **587×**，每檔約 **10.56ms**；其中 `os.path.isfile` 一項佔 40%（250 檔：isfile 732ms vs open+read 1092ms）⇒ **EAFP 取代 LBYL 在 drvfs 上是實質優化、不是風格偏好**。★**反直覺的那一半**：9p 雖掛載成單一 transport（`trans=fd,rfd=6,wfd=6`），卻**支援並發 in-flight 請求**——同批檔案序列 2572ms／並行 4 為 526ms（4.89×）／並行 8 為 406ms（**6.33×**）⇒ 「單通道所以並行無用」是錯的，延遲可以重疊。★**三個可複用的手法**（本批實得 43.46s→13.09s、3.3×）：①行程層並行派發（各閘唯讀、無共享可變狀態時直接背景跑＋收斂）②同輪內重複讀的作用域快取（`docs-sync` 的 `_read` 971 次呼叫只碰 380 個唯一檔案＝重複率 2.56×）③subprocess 密集處並行預取（`fork-delta-lint` 的 `git show` 逐檔取基線原文，預取只把等待重疊、判定順序一字不動 ⇒ 輸出逐位元組相同）。★**快取的正確作法是「限作用域」而非行程級常駐**：`generate` 會寫檔後再讀、自測 529 案各自建臨時 repo 並就地改檔——常駐快取會讓兩者讀到過期內容，那是把效能修成正確性缺陷。★**歸因紀律**：動手前先 cProfile 分「I/O 稅 vs 邏輯」，否則優化的是那 7%；且合成推估會系統性誤導——本批同時發現 `wire-schema check --staged-gate` 的真路徑僅 0.43s，而合成公式沿用的是未短路路徑的 8.431s。★`/home/anew/x_Project` 是 symlink 指向 `/mnt/d/AnewSpaces/x_Project`（device+inode 相同）、不是原生 ext4 副本——挑 performance-sensitive path 時誤用它＝零收益（B-133）。
