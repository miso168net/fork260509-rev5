- **L-078**｜**fix agent 因「finding 指涉的檔在允許清單外」而正確地零改動時，script 的「連兩輪零改動＝不收斂」偵測會把這個正確反應判成故障，白跑兩輪 review**：防呆⑤的零改動偵測是為了抓「fix 空轉」（改不動也講不出理由），但它與防呆⑥的正確反應**共用同一個外觀**——`filesChanged: []`。差別在 `status`：空轉是 `ok`＋零改動，正確升級是 `done_with_escalation`＋零改動＋escalations 有內容。script 若只看 `filesChanged` 長度，兩者無從分辨。★**2026-09-01 實暴**（008 之契約錨單元）：唯一的 blocker 指向 `specs/…/data-model.md`（本單元允許清單的「不得動」項），fix agent 依防呆⑥正確地不擅改、逐輪回 `done_with_escalation`，跑滿兩輪後被判「⑤收斂偵測：fix 連兩輪零改動」而 unresolved——結論**功能上正確**（主線收到了 blocker 並自行處置），代價是多跑了兩支 review agent，且 return 的 `reason` 講的是「不收斂」而非真正的原因「清單外待辦待主線處置」，主線得讀完 blocker 才知道。★**判別問句**：這一輪零改動，是「改不動」還是「不該由我改」？後者 script 應該當場收工升級，不是再問一次審查員。★**防法**：`cycle()` 內對 fix 回傳加一格——`if (fx.status === 'done_with_escalation' && (fx.filesChanged||[]).length === 0) return { converged:false, reason:'fix 判 findings 全落允許清單外、已升級', blockers, escalations: fx.escalations }`；置於零改動偵測**之前**。零改動偵測自此只服務 `status: ok` 的真空轉。
