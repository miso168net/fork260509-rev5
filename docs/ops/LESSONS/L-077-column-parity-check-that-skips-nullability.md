- **L-077**｜**「逐欄對賬 schema 真源」若只驗欄名與存在性、不驗可空性，文件裡的型別失真會整條穿過復核，而且下游是照文件施工的**：派工單常把「欄集逐字＝data-model §N」寫成實作依據，於是文件裡一格 `string|null` vs 真源 `NOT NULL` 的差，會變成下一支 implementer 寫出 `Option<String>` 的 DTO——而該 DTO 要到再下一個單元的 wire 快照裁判才炸，屆時讀者會先懷疑裁判基準而不是文件。★**2026-09-01 實暴**（008 之契約錨單元，**主線自身的復核缺陷**）：主線先前宣告「data-model §1 四表逐欄對賬 entity 真源＝全部一致」，比對的其實只有**欄的數量與存在性**；碼品質審查員逐格核對型別時抓出 §1.1 的 `realIp` 記為 `string\|null`，而三張表的 entity 皆為 `real_ip: IpNetwork`（非 `Option`）＝NOT NULL（憲法 1.6.0 log 亦逐字載「rev5 的 `sys_operation_log.real_ip` 是 `inet NOT NULL`（rev4 可空）」），且同檔 §1.2／§1.3 對另兩表已正確寫 `(string NN)`——單點落字、不是設計分岔。★**判別問句**：我說的「逐欄一致」，是逐欄**看過型別欄**，還是只數了欄數對得上？後者在欄數相同時**恆綠**，而欄數相同正是最常見的情形。★**防法**：①對賬腳本化——把真源（entity 的 `Option<T>` 與否／migration 的 `.not_null()`）與文件表拉成兩個 `{欄名: 可空性}` dict 做集合比對，別用眼睛掃②可空性失真**優先看 schema**（migration／entity），文件與 typings 都是它的下游③同一份文件內若同型欄在別節寫法不同（一處 `\|null`、一處 `NN`），那個不一致本身就是失真的訊號。
