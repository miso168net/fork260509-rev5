- **L-084**｜**CDP 走查的 UPDATE 型副作用對「列數基準」結構性不可見——`walkthrough-baseline diff` 綠不等於環境已還原**：`tools/walkthrough-baseline.py` 的三個比對面是**全部表列數／全部序列 last_value＋is_called／redis DBSIZE 與逐前綴鍵數**——三面都是**計數**，沒有一面比**內容**。走查若只做 INSERT 型操作（登入產 `sys_login_attempt`／`sys_token` 列、redis session 鍵），計數會變、baseline 抓得到；但走查若**改了一筆既有列的值**（管理頁的本職就是這件事），列數、序列、redis 鍵數**一個都不動** ⇒ baseline 結構性看不見它。★**2026-09-02 實暴（本刀 U7、settings 頁 CDP 走查）**：走查「改一鍵回讀」切換了 `system_settings.password_require_digit`（`off`→`on`→`off`）。我把值改回去了、照 §9c 步驟 3 清完 `sys_login_attempt`／`sys_token`／兩個 seq／redis session 鍵，步驟 4 的 `walkthrough-baseline diff` **rc=0 全等**——看起來完全還原。但步驟 6 的 `python3 tools/schema-gate.py check` **紅**：gate2 的 seed 逐列 diff 印出 `-password_require_digit … \N \N …` ／ `+password_require_digit … 2026-09-01 19:55:21 1 …`——**`setting_value` 已回 `off`、`updated_at` 與 `updated_by` 沒回**。憲法 §I.6 的業務表審計欄標準讓每一次 UPDATE 都留痕，而「把值改回去」只還原了值、沒還原痕。清掉那兩欄後兩者皆綠。★**為何 §9c 的六步序仍然接住了它**：步驟 4 的註記逐字寫著「**rc 0 為準、非三閘綠**」（防的是「三閘綠而全量紅」），而本案是**反方向**——baseline 綠而三閘紅；兩道網覆蓋面互補、缺一都會漏，六步把兩者都排進去正是為此。真正的缺口在**步驟 3 對「清理面」的舉例**：全是 INSERT 型，讀者照舉例做完就會以為清乾淨了。★**防法**：①走查前先問「這次走查會**改**什麼，不只是**寫**什麼」——凡動到既有列的值，清理面就包含**該列的審計欄**（`updated_at`／`updated_by`；有些表另有 `version`／`revision` 類欄），不是把值改回去就結束②`walkthrough-baseline diff` rc=0 **不是**還原完成的判準，它只是六步中的一步——**步驟 6 的三閘（尤其 `schema-gate` gate2 的逐列 diff）才看得見內容面**，兩者都綠才算還原③反過來說：本條不建議把內容比對加進 `walkthrough-baseline`——那會與 `schema-gate` gate2 重複造第二份 seed 對賬面（單一權威原則），正解是**清理面的定義寫對**。★**一般化**：對賬工具的盲區由它**比什麼**決定，而不是由它**掃多寬**決定——`walkthrough-baseline` 掃遍 public schema 全部表（比任何閘都寬），卻對「同一列換了內容」完全無感。判斷一道對賬能不能替代另一道，看的是比對維度，不是覆蓋範圍。相關：[[L-055-runtime-append-residue-blows-next-full-suite]]（同域另一半：INSERT 型殘列＋seq 復位）、[[L-032-historical-statements-stay-present-tense-gets-fixed]]。
