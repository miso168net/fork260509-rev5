- **L-059**｜**守門 lint 若「結構走 A 視圖、字面查 B 視圖」，兩視圖必須逐 byte 對齊、屬性字面按精確 (起, 迄) 圈界；退成「以行為粒度」查表，即在「同一行擠多個語法元素」時讓相鄰元素互借字面——未守衛欄被靜默判成已守衛（假陰性、主守恆恆綠）**：刀 B 前置維護批 U2（2026-08-25）建 `wire_i64_guard_lint`（B-111）時，判準需要同時看兩件事——①欄位的**結構**（型別、括號配對、屬性組邊界）②屬性裡**字串常值的內容**（`serialize_with = "…guarded"` 掛的是哪一支 serializer）。既有的 `common::strip_comments_and_literals` 把字串常值**連同引號一起丟掉**，於是 `#[serde(serialize_with = "…guarded")]` 只剩 `#[serde(serialize_with = )]`：「屬性在不在」看得見、「掛的是哪一支」看不見，判準會退化成「有掛 serialize_with 就算數」。反過來，結構解析又**不能**用保留常值的視圖（常值內的 `{`／`}` 會弄壞括號配對）。故必然是雙視圖。★**真正的坑不在雙視圖本身，而在兩視圖的座標系**：第一版以「行號」對應兩視圖並按行查字面，看似安全——因為「rustfmt 會保證一欄一行」。★**該假設實測為假，而且成因正是本 repo 自己的格式設定**：容器內套 repo 的 `rust-api/rustfmt.toml` 實測，`pub struct P(#[serde(serialize_with = "a")] pub i64, #[serde(serialize_with = "b")] pub i64);` 經 `rustfmt --edition 2024` **逐字不變**——兩個帶屬性的 i64 欄留在同一行；而拿掉該設定跑裸 rustfmt（預設 heuristics），同一段**會**被拆成一欄一行。差別來源＝ADR 0057 拍板的 `use_small_heuristics = "Max"`（該值是為了讓存量格式化的 diff 最小而選：675 段 vs 全預設 1,649 段）。也就是說「一欄一行」不只是不成立，它**因本 repo 的格式拍板而不成立**，且具名欄面（`struct N { #[attr] pub x: i64, … }`）確實會被拆、只有 tuple 欄面不會——這種「只有一半成立」的假設最容易讓人放心。★**危害形**：同一行上第二個欄去查表，借到第一個欄的屬性字面 ⇒ 清白與否顛倒；且方向是**假陰性**（未守衛判成已守衛），主守恆的集合恰等會完全恆綠、沒有任何訊號。★**防法**：新增一個**常值逐 byte 換白（長度不變、換行保留）**的結構視圖，與字面視圖共用同一組 byte 偏移；屬性字面一律按解析得到的精確 `(起, 迄)` 圈界取用，永不按行取。實例＝`wire_i64_guard_lint` 的 `same_line_fields_do_not_borrow_each_others_attrs`（同一行兩個帶屬性 tuple 欄、一個守衛一個不守衛，借錯即紅）與 `strip_views_are_offset_aligned`（兩視圖 byte 偏移逐位對應的前提自證——前提一失效，上面所有判定都在比對別處的文字，且完全無聲）。★**連帶心得**：這類「前提假設」測（本例＝兩視圖對齊）本身就是 ADR 0024 要求②的一種——它守的不是被測物，是**判準自己的成立條件**；沒有它，閘壞掉的方式是「安靜地永遠通過」。
