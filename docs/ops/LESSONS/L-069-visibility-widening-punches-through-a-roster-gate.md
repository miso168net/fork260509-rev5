- **L-069**｜**把一個函式的可見性放寬，可能當場把一道既有機器閘的射程打穿——而且全樹零紅點**：本 repo 有一道 `RELOAD_CALL_FILES` 名冊閘，判準是「`src/` 全樹中出現 `reload_enforcer` **token** 的檔集合須恰等於名冊」，用途是「擴列＝新增 casbin 熱套觸發點，須先對照 ADR 0053 款四觸發矩陣拍板」。★**2026-08-29 實暴**（本刀 U4）：為了讓 `handler::user_center` 與 user 管理面共用同一條「commit→denylist 廣播→條件式 reload」收尾腿（FR-007 零拷貝，本身完全正確），把 `handler/user.rs::finish_user_write` 由私有提升為 `pub(crate)`——而 `handler/user.rs` **唯一那行 `reload_enforcer(state).await` 就住在它體內**。自此任何 handler 都能 `use crate::handler::user::finish_user_write` 並傳 `reload = true` 觸發全域熱套，而**該檔不會出現 `reload_enforcer` 這個 token** ⇒ 名冊閘照樣綠、觸發矩陣也不會被覆核。★**危險在於它偽裝成安全**：U4 自己製造的第一個名冊外間接觸發者（`user_center.rs`）傳的是 `false`，且那個實參另有 reload 矩陣測在守——但那守的是**這一個呼叫點的實參**，不是「名冊仍涵蓋全部觸發面」這件事。兩者是不同的不變式，混為一談就會覺得已經有守了。★**根因**＝**token 掃描型閘的射程綁在「效果的字面出現在哪個檔」，而可見性放寬讓同一個效果可以從別的檔觸發、且不帶那個字面**。同族的閘（寫面名冊、entity 存取面、i18n 鍵集）皆有此形。★**防法**：①改動可見性時，先 grep 該函式體內有沒有任何「被 token 掃描閘守著」的呼叫（`reload_enforcer`、`enforcer` 寫鎖、`entity::` 等）②有的話，同批補一道**消費者名冊閘**（家檔＝定義處，名冊＝跨檔消費者），並把「擴列須對照哪張矩陣拍板」寫進名冊 doc③兩道閘的 doc 互相指路，講清楚一道守直呼形、一道守間接形，免得後人以為重複而刪掉其中一道。★**一般化**：機器閘的判準（掃什麼 token、在哪些檔掃）與它宣稱要守的不變式（「全部觸發面都經過拍板」）之間永遠有距離，而那段距離會隨碼演化而擴大——**改動如果縮短了「效果」與「字面」之間的耦合，就要回頭問一次那道閘還在守著什麼**。相關：[[L-068-agent-fuse-below-structural-worst-case-fires-on-healthy-runs]]（同族：機器守的判準要與被守物同源）、[[L-067-lint25-unit-round-shape-traps-current-generation-too]]。
