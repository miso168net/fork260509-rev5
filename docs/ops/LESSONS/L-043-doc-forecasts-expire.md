- **L-043**｜**文件裡的「預告」是一種會過期的斷言，而且比一般假述更難察覺——因為它在寫下的當時是對的**：004 U-H 在 `facade/sys_operation_log.rs` 檔頭寫下「rev5 **不預先開**第二支非交易寫端——解鎖屬 U-K，且其次序要求與本函式不同軸，**屆時由該刀依自己的語意開**」（引文略去原句的裸 user story 號，ADR 0012 命名空間紀律）。那是**當時最好的判斷**（simplicity-first：不留沒有消費者的口）。但 U-K 落地後的 as-built 是：解鎖端點用 `state.db.begin()` → **既有的** `write_in_txn` → `commit` 寫**單列交易**就滿足了「先落稽核列、後動快取」，第二支寫端**不需要、也沒開**。⇒ 讀該檔的人會去找一支**不存在的函式**。★**為何比一般假述難察覺**：①它不是「現況描述」而是「未來安排」，覆核時很容易當成「這條還沒到期、不用查」②它的失效條件是「未來那刀做了**別的**選擇」，而做選擇的人（U-K 的 implementer）通常不會回頭去讀**上一刀**的檔頭註 ③沒有任何機器守——預告落空不會編譯紅、不會測試紅。★**判斷錯在哪（值得記，因為同型會再犯）**：原文以為「次序要求不同軸」蘊含「需要不同的寫端」，實則**次序要求的差別在跨系統的先後（DB→快取），不在交易與否**——單列交易一樣滿足它。把「兩件事不一樣」直接推成「需要兩套機制」是常見的過度推論。★**防法**：①文件寫預告時 MUST 標成預告並附**回填義務**（形如「★**as-built 待回填**：X 刀落地後回來把本段改成實況，無論結果是否如預期」）②該刀的 tasks 條文同批加一句「回填 §X 的預告」——沒有這一句，回填就只能靠人記得 ③覆核時把「屆時／日後／將由」當**同義集關鍵詞**掃（L-038），它們是預告的語言指紋。
