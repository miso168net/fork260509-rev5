- **L-063**｜**憲法 §III.2 開新 ★ 軌道用途時，Amendment 當下做的「新列變異自證」結構性 vacuous——會回綠、看起來像守門有效，其實一次都沒觸發**：`fork-delta-lint` 驗的是（軌道×用途×檔案）三元組，掃描面是**碼裡實際存在的 `rev5-inline` 標記**；新用途在 Amendment 落地那一刻**尚無任何標記**（碼還沒動、且多半正被同一份 Amendment 的硬閘凍結著），故把該列範圍欄的路徑改成裸措辭 → 零標記可比 → **rc=0**。★**2026-08-27 實證**（007 之 T003，憲法 v1.9.0 開 MANAGE-PAGE-WIRING (v)(vi)＋LOGIN-CAPTCHA-WIRING (ii)）：改壞新列 (v) 的 `src/views/manage/user/index.vue` 路徑 → `fork-delta-lint` **rc=0**；同一手法改壞**已有標記**的 (ii) 列（`src/views/manage/role/index.vue`）→ **rc=1、5 筆 findings**（「檔 … 不在 ★軌道 …(ii) 授權檔案集（B-068 三元組第 3 維不合）」）⇒ 守門本身非 vacuous，vacuous 的是**時點**。★**危害**：Amendment 的 commit message 會逐字寫下「新列變異自證已跑、紅證如附」，而那次紅證根本不存在——下一個讀者會據此相信該列已有機器守，於是**跳過**真正該做的那次驗證；這正是 ADR 0024「非 vacuous 守門」要防的形，只是換到治理層。★**防法**：①開新用途的 Amendment task 只宣稱「守門機制已驗（拿已有標記的既有列反證）」，**不得**宣稱新列自身已驗；②把新列的真變異自證**排進第一個往該列落標記的實作單元**（本刀＝U6 之 index.vue／U7 之 user-center 與 unlock modal／U8 之 pwd-login），且紅證逐字補記該 task；③一般化的前提檢查＝**變異測試之前先確認「被守的那一面已經有實例」**（沒有實例就沒有可被變壞的東西，測的是空集合）。★**還原紀律照 L-060**：全程以「存原文→寫回」還原、`md5sum` 對照，不用 `git checkout`（同檔另有本次 Amendment 的未 commit 改動）。
