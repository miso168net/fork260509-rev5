- **L-080**｜**盤點「本單元會連動哪些釘值」時只找數字常數，會漏掉手抄的檔案名冊——因為新增一個檔案本身就是一次「集合改變」，而它不長得像數字**：連動面的直覺搜法是 `grep` 那個要改的數（`ROUTES_COUNT`、`61`、計數註），這抓得到計數型釘；但另一類守門是**手抄名冊＋枚舉對賬測**（「`src/` 下符合判準的檔案都要在這張表裡」），它的觸發條件不是「數字變了」而是「**多了一個符合判準的檔**」——新開一支 handler 就命中，而盤點時完全不會想到去 grep 它。★**2026-09-01 實暴**（008 之讀面單元）：主線盤點連動面時抓到了 `handler/role.rs` 的 `POLICY_ENDPOINT_COUNT`（數字釘）與同測的 `got.last()` 逐字釘，**漏掉** `envelope.rs` 的 `B043_SCAN_FILES`——一張 23 列的手抄檔案名冊，配一支枚舉 `src/**/*.rs` 的對賬測，判準逐字＝「`handler/` 全檔、或全文含 `Res::ok` 之檔必在名冊內」。新開的 `handler/audit.rs` 兩個條件都命中卻沒補進去 ⇒ 容器內全量 serial **rc=101、1 failed**。★實害不只是一支測紅：漏冊代表該檔**永不被 B-043 守門測掃**，日後在其中寫出 `(StatusCode::X, Res::ok(payload))` 這種自相矛盾的回應會零紅點。★**判別問句**：本單元**新增了哪些檔**？全樹有哪些「以檔案清單為受檢面」的斷言，其判準會涵蓋這些新檔？★**防法**：①盤點連動面時**兩路並行**——數字釘走 `grep <值>`、名冊釘走 `grep -rln "include_str!\|指定副檔名枚舉\|walkdir\|read_dir"` 於測試碼與 lint 面②新增檔的單元，把「跑一次全量測試」排在**實作早期**而非收尾（名冊型對賬測會立刻紅、且訊息直接指名該補哪一列）③名冊型守門自己要在 panic 訊息裡寫清判準與補法——本案的 `envelope.rs` 做到了，所以 review 一眼就給出了正確修法與插入位。
