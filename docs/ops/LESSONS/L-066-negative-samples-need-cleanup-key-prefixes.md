- **L-066**｜**「應該被拒」的測試樣本也必須帶清理鍵前綴——因為守門一旦被改壞，那一發就真的會建出一列，而那列不帶前綴、清理守衛圈不到**：本 repo 的清理守衛以「顯式大 id」與「業務鍵前綴」雙名冊為鍵（`UserCleanup::with_name_prefixes`／`RoleCleanup` 的業務鍵腿）。撰測時很自然會給負向樣本一個「一看就知道會被拒」的裸字面（例：形制不合的 `"壞 名字!"`），理由是「它反正不會落庫」——★**這個前提正好在變異測試時失效**：驗證守門非 vacuous 的整個動作，就是讓守門失效一次、看那一發會不會落庫。★**2026-08-28 實暴**（本刀 U2／T023）：`addUser` 形制守門的變異驗紅漏出一列 `id=4` 的殘列，該列的 `user_name` 是裸字面 ⇒ 兩個名冊腿都圈不到，且 `sys_user_id_seq` 被 `nextval` 不可逆推進——`sys_user` 在 `RUNTIME_APPEND_TABLES` 之外，gate2 seed 逐列全等當場紅，需人工刮列＋`setval('sys_user_id_seq', 3, true)` 善後。★**防法**：負向樣本用「帶前綴但仍違規」的構造，例 `format!("{}!", uniq_key("t023add"))`——前綴讓守衛圈得到、尾綴讓它必然違規，兩個目的不衝突。★**一般化的判別問句**：這個樣本如果**沒有**被拒，會在庫裡留下什麼？留得下東西就得帶清理鍵。相關：[[L-065-destructive-guard-mutation-really-destroys-seed]]。
