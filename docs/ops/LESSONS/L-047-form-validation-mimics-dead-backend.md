- **L-047**｜**前端表單驗證擋下的提交，症狀是「零網路請求＋零 toast」——與「後端掛了」「請求被中間層吞掉」完全同形**：004 收刀後以 CDP 走查節流行為時實暴，浪費一輪排查。機制：拿 `wrong-password` 當錯誤密碼送登入表單，畫面毫無動靜、`sys_login_attempt` 零新列——看起來像後端沒反應；真因是 `base-web` 的 `REG_PWD = /^\w{6,18}$/`（基線碼）判定該字面不合格（含連字號），`NForm.validate()` 直接 reject，**請求根本沒發出去**。唯一線索是表單欄位下方一行小字 feedback，而截圖與 `innerText` 摘要都很容易漏掉它。★**這在本 repo 有具體踩點面、不是泛泛的除錯常識**：`specs/*/quickstart.md` 的節流走查全程用 **curl**，密碼字面用 `"wrong"`（5 字元）與 `"x"`（1 字元）——**兩者都會被前端表單擋掉** ⇒ 想從 UI 重現 quickstart 的三區行為的人，會在第一步就撞上這個，且症狀指向後端。兩條路徑的**可達輸入集不同**，走查文件沒說。★**防法**：①排查任何後端行為（節流、權限、錯誤碼）前，**先確認請求真的發出去了**——CDP 驅動時在點提交**之前**掛 `Network.enable` ＋ `Network.requestWillBeSent` 監聽，零請求即當場判定是前端擋的，不要去翻後端 log；②走查文件若同時存在 curl 與 UI 兩條路徑，**用的字面 MUST 同時滿足兩條路徑的驗證**，否則就明寫「本節字面走 curl 專用、UI 重現須換合規值」（004 quickstart §4 已補該註）；③讀 UI 狀態時把 `.n-form-item-feedback__line`（或等價的表單回饋節點）納入例行輸出——它是這一類失效的**唯一**訊號。
