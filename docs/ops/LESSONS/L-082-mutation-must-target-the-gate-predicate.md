- **L-082**｜**補完守門做變異測試時，若注入的形正好落在該閘「刻意排除」的那一類，變異不會紅——而那看起來與「閘是恆綠的」一模一樣**：[[L-073]] 記過「變異沒紅有三種成因：守門真 vacuous／變異沒打到那一格／那些案根本沒跑」，本條是**第二種的具體形**：閘的判準往往比「出現這個 token」窄（只抓呼叫形、只抓修改型、只抓某目錄），而寫變異的人憑「這個字出現了就該被抓到」的直覺去注入，正好注進被排除的那一格。★**2026-09-01 實暴**（008 之 purge 下沉單元，主線自身）：新補的 `purge_before` 呼叫點名冊閘，變異時在名冊外的檔注入 `fn purge_before() {}`（**定義**形）→ 閘**沒紅**、`1 passed`。加臨時 `eprintln!` 診斷才看清：`scanned=60` 但 hits 只有五檔、且行號全落在測試區——因為底座 `call_lines_of` 的判準逐字是「後（容空白）隨 `(`＝呼叫形；**排除 `fn <pat>(` 定義處**」（另有具名 helper `preceded_by_fn_keyword`）。改注入**呼叫形**（`crate::model::facade::sys_operation_log::purge_before(txn, 30)`）後閘當場紅、訊息指名 `handler/captcha.rs:93`。★**同一次診斷還揭穿了第二個錯**：主線寫的名冊 doc 說「前四檔＝定義處」，實際上定義處根本不入 hits、那四筆是各 facade **自家測試區的呼叫**——doc 與 as-built 分岔而全綠。★**判別問句**：這個閘的判準**排除**了什麼？我的變異是不是正好長成被排除的那個樣子？★**防法**：①注入變異**前**先讀底座 detector 的 doc 與排除條件（本案的 `call_lines_of` doc 逐字寫明了排除面）②變異沒紅時**先加診斷輸出**（印 scanned 與 hits）自證「變異有沒有進到受檢面」，再談閘是否 vacuous——直接下「閘壞了」或「閘沒問題」的結論都是猜③閘的 doc 自陳「本閘的變異紅證該注入什麼形」，讓下一個補變異的人不必重新推理。
