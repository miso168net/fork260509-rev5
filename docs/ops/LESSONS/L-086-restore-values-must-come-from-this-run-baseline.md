- **L-086**｜**走查還原的 `setval` 目標值沿用上一次走查的指令＝把序列往回撥**：§9c 步驟 3 要求「runtime-append 四表清列＋各自 seq 復位」，而復位指令長得像個可以複製的模板（`SELECT setval('sys_token_id_seq', 35252, true)`）——★**但那個數字是上一次走查當下的值**。兩次走查之間，環境會被**別的活動**推進：容器內全量測試每跑一輪就插一批 runtime-append 列、workflow agent 的 fix 輪也在跑測試、dev server 服務任何請求都可能落列。★**2026-09-02 實暴（本刀 U8 收單的 CDP 快查）**：我把 U7 走查用過的 `setval` 指令整段複製過來，數字沒換——`sys_login_attempt_id_seq` 被由 **86471 撥回 86233**（−238）、`sys_token_id_seq` 由 **35358 撥回 35252**（−106）。兩次走查之間隔了 U8 那支 workflow（10 支 agent、含多輪容器內測試），序列早已前進。★**危害方向與 L-055 相反、嚴重性相當**：往前漏復位是「下一輪撞殘留列」，往**回**撥是「下一輪插入撞**已存在的 id**」——同樣是 23505 唯一鍵衝突，同樣「殘留與爆點隔一整輪」。本次因表已被 `DELETE` 清空而沒有立即爆，**那是運氣不是設計**。★**抓到它的是流程本身**：§9c 步驟 4 的 `walkthrough-baseline diff` 當場報「序列 2 項差」並印出**負的差值**（`-238`／`-106`）——負差值是這個坑的招牌徵狀（正差值＝沒復位，負差值＝復位到舊值）。⇒ 六步序沒有失效，失效的是我把「還原」當成可以憑記憶執行的動作。★**防法**：①`setval` 的目標值 **MUST 自本次 `walkthrough-baseline.json` 讀出**（該檔的 `sequences.<seq>.last_value`），**永遠不要**從上一次的指令複製數字②清理指令**每次現組**、不要維護一份「走查清理模板」——模板化的正是那個會過期的部分③看 `diff` 輸出時**注意差值的正負號**：正＝殘留未清，負＝復位過頭。★**一般化**：凡是「把環境還原到某個先前狀態」的動作，**目標狀態必須現讀、不能記憶**——因為兩次操作之間環境屬於所有人，不只屬於你。這與 [[L-032-historical-statements-stay-present-tense-gets-fixed]] 的精神同源：記在指令裡的值和寫在文件裡的敘述一樣會過期，差別只在前者過期時是靜默破壞環境。
