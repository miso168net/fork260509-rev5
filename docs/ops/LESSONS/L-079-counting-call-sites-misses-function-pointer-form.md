- **L-079**｜**驗「某函式的呼叫處恰 N 處」時只 grep `name(`，會漏掉函式指標傳遞形（`.map(name)`／`.and_then(name)`／`.unwrap_or_else(name)`），得到 0 命中而誤判成「根本沒呼叫」**：派工單常把安全要求寫成處數（例如「PII 打碼呼叫**恰二處**」），驗收就照著數；但 rust／JS 這類把函式當值傳的語言裡，呼叫可以完全不帶括號。★**2026-09-01 實暴**（008 之讀面單元復核，主線自身）：`grep -c "mask_pii_payload(" handler/audit.rs` 回 **0**，主線一度判定「FR-B02 的 PII 打碼未落地」——實際碼是 `payload_before: m.payload_before.map(mask_pii_payload)` 與 `payload_after: ….map(mask_pii_payload)`，**恰二處、完全正確**。假陰性的方向特別壞：它讓你以為安全要求沒做，接著可能去「補上」而變成打碼兩次。★**判別問句**：這個函式在這個語言裡，有沒有不帶括號就被呼叫的寫法？（rust 的 `map`／`filter_map`／`ok_or_else`、JS 的 `.map(fn)`、python 的 `key=fn`——都有。）★**防法**：①數呼叫處一律取三形聯集：`grep -nE "\bname\s*\(|\(\s*name\s*\)|::name\b"`②更穩的是**問編譯器不問 grep**——臨時把該 fn 改名再編譯，錯誤訊息會列出全部真實使用點（改完還原；還原紀律照 [[L-060-restore-temp-mutation-without-git-checkout]]）③處數型驗收若要長期有效，該由**測試**釘（例如對賬測掃 AST／掃 include_str 文本），不是由人每次 grep。
