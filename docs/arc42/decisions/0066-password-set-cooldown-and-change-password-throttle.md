## 背景

本刀讓兩個「限制重試」的機制在同一條路徑上同時進場，它們形似到很容易被寫成同一個東西：

- **設密冷卻**：同一對 (標的, 操作者) 兩次設定密碼之間要隔多久。
- **改密舊密節流**：`changePassword` 的「舊密碼」欄在窗內可以猜錯幾次。

兩者都以時間為單位、都在密碼路徑上、都會回「你太頻繁了」語意的拒絕。但它們擋的是不同的東西，
而 BACKLOG 有兩條懸而未決的條目正好各壓一半：B-021 明列兩個殘餘拍板點（redis 故障要 fail-open
還是 fail-closed、門檻走設定鍵還是常數），B-020 則把「節流通用 seam 要不要做」的定案排到本刀。

★**改密節流在 rev4 是零實作**（其 rev4:B-102 承載未做），故無藍本可循；設密冷卻則有
rev4:015-pwd-custody 的拍板可借。

## 決定

### 一、設密冷卻——業務政策，走設定鍵

- **維度＝(標的 id, 操作者 id) 這一對**（`sys_pwd_custody` 複合 PK）。不同管理員各記各的：
  A 剛替某人重設過，不會讓 B 也被擋。自助改密是 `(uid, uid)` 這一對、自成一格。
- **料源＝`sys_pwd_custody` 只存時戳**，表內零密碼材料（憲法 §I.7 島 I5）。★rev4 另有一支
  「密碼是否由他人代設」的 `EXISTS` 判定，服務的是首登強制改密整包——rev5 不做（B-134、
  research R2-22），連帶 rev4「本人自改→全刪他人經手列」的語意亦不帶回（R2-27：rev5 只 upsert）。
- **門檻＝設定鍵 `password_change_min_interval`**，`0` ＝停用（早退、連 custody 都不查）。
  讀不到設定列時的 fail-default ＝**回到出廠設定**（m002 seed 值 60），不是「壞掉就從嚴」也不是
  「壞掉就放行」；同 `PasswordPolicy::default` 的取態。
- **首寫免判、但 custody 照落**：`addUser` 的初始密碼對 (新 id, operator) 沒有前一次可比 ⇒ 放行，
  但 `touch` 照樣寫——初始密碼計入冷卻帳，否則「建帳後立刻重設」會白得一次免費機會。
- `touch` MUST 與密碼欄 UPDATE **同一交易**（島 I1 的 advisory 序列化域內）：分兩個交易就會有
  「密碼改了、冷卻帳沒記」的窗，那正是繞過冷卻的縫。

### 二、改密舊密節流——安全參數，走碼內常數

- **門檻＝碼內常數**：`CHANGE_PWD_MAX_FAILS = 5`、`CHANGE_PWD_WINDOW_SECS = 900`。
  **不入 `system_settings`**（data-model §2 逐字）。
- **方向＝fail-open**（結 B-021 殘餘拍板點之一）：redis 問不到時放行並記一筆降級。代價不對稱——
  節流是「防慢速猜測」的加值防線，快取失聯期間 fail-closed 等於讓全體使用者在快取壞掉的整段時間
  內都改不了密碼（含正在應變資安事件、急著換密碼的那個人）；fail-open 的代價是那段時間內猜測者
  多得到幾次嘗試，其上界仍受舊密碼本身強度與 access token 壽命所限。★方向與 denylist 的
  fail-closed 相反是刻意的（data-model §5），兩者護的東西不同。
- **拒絕點在 argon2 verify 之前**，且**拒絕路徑零計數推進**——否則自動化工具只要持續打，就能把
  任何人的改密功能鎖死（同 `throttle::precheck` 三個拒絕分支的紀律）。
- **拒因純 key**（`biz.user.changePasswordThrottled`），**不下發剩餘秒數或已用次數**：那些數字是
  桶的當前狀態，下發等於給猜測者一個可查詢的預言機。★與冷卻攜參形成對比，判準見 ADR 0064 決定二。
- **觀測自成一源**：`redis_change_pwd`（`THROTTLE_DEGRADED_SOURCES` 第 13 格），**不經**
  `throttle::warn_degraded`——那支的 `source` 語意是「登入節流的哪一腿降級」。
- **快取鍵前綴 `cpwd:` 與 `throttle:` 分離**：維運面的 `KEYS throttle:*` 批次清鍵不該把另一把鎖
  一起掃掉。

### 三、★門檻進不進設定表的判準＝「這個數字的正確值是否隨組織而異」

同一把刀裡兩個門檻走了相反的路，判準只有這一條：

- **冷卻進設定表**——「管理員多久能替同一人重設一次密碼」沒有普世正確答案，不同組織的運維節奏
  不同，而且 `0`＝停用是一個有意義的選擇。
- **節流不進設定表**——「舊密碼可以猜幾次」的正確值只有一個量級。把它做成旋鈕，唯一會發生的事
  是有人為了排解某次誤擋而調鬆它，然後那個值就永遠留在那裡。且每個設定鍵都要付一串固定成本
  （`validation.rs` 界限表、設定頁 UI、wire 契約、seed 列、兩語 i18n），為一個只會被調錯的旋鈕
  付這串成本是負收益。

★**不是「安全的就寫死、業務的就可調」**——那是結論不是判準。判準是問這個數字有沒有第二個
合理答案；有，才值得一個旋鈕。

### 四、兩者不合併，且不做通用節流 seam（B-020 通用化半邊判 won't-fix、關帳）

B-020 的觸發條件（「第二個消費者存在」）在本刀**確實成立**了，但結論仍是不通用化——因為兩個
消費者在四個面上都不同形：

| 面 | 登入節流 | 改密節流 |
|---|---|---|
| 判定鍵 | 帳號名／IP bucket（**未驗身**） | uid（**已驗身、不可竄改**） |
| 語意分區 | 自由區／軟區（captcha）／硬鎖 **三區** | 過或拒 **兩態**，沒有 captcha 這回事 |
| 觀測 | `throttle::warn_degraded` 的十二源 | 自成第 13 源 |
| 鍵面 | `throttle:` | `cpwd:` |

抽一個能同時容納三區與兩態的共用 seam，等於為兩個形狀不同的消費者硬造抽象；`throttle::precheck`
的簽章也會被迫長出「這次要不要 captcha」之類的參數。**B-020 之通用化半邊自此判 won't-fix**
（per-IP 半邊已於 004-ip-trust-anchor 交付），條目關帳。★翻案觸發器＝出現**第三個**消費者且其
形制與既有兩者之一同形——屆時「兩個特例」才會變成「一個模式」。

## 替代案

**A. 節流門檻也進 `system_settings`（與冷卻一致）。** 未採——理由見決定三；「一致」本身不是價值，
兩個數字的性質不同就該走不同的路，硬求一致反而讓判準消失。

**B. 改密節流 fail-closed。** 未採——代價不對稱（決定二）。★誠實記：這個選擇讓 redis 失聯期間
存在一段真空，本 ADR 不假裝它不存在；它的補償是 access token 壽命有限、且降級有觀測源可告警。

**C. 冷卻與節流合併成一個「密碼操作頻率限制」。** 未採——冷卻擋的是「你太常改密碼」（對象是
**成功**的操作），節流擋的是「你一直猜錯」（對象是**失敗**的嘗試）。合併後，一個成功改密的人
會被失敗計數影響，或反之；而兩者的正確反應（等一下 vs. 你可能不是本人）根本不同。

## 後果

- B-021 關帳（改密端點舊密節流已交付，兩個殘餘拍板點由決定二結掉）；B-020 關帳（通用化半邊
  won't-fix，翻案觸發器見決定四末句）。
- ★**誠實記——「被節流的請求不吃 CPU」這個推論自本刀 U4 起失效**：拒絕路徑仍零 argon2 **verify**，
  但新密碼的**雜湊生成**已移到 handler、在開交易之前發生（憲法 §I.7 島 I5 末句、ADR 0068）⇒
  被節流擋下的請求同樣會白算一次 argon2 生成。做容量或防濫用判斷時不可據舊述推論；同口徑的
  記載已落在 `throttle/change_pwd.rs` 模組 doc 與兩處 fn doc。
- ★**留給後人的判準**（決定三）：新增門檻先問「這個數字有沒有第二個合理答案」——有才給旋鈕。
- 本 ADR **零碼改動**：as-built 已於本刀 U1（T010／T020）與 U4（T045）落地。
