## 背景

`sys_user.user_phone` 的長度約束在本刀收官時有**四個權威、三種說法**：

| 權威 | 說法 | 查證 |
|---|---|---|
| spec FR-008 | 「手機（選填、**≤32**）」 | 逐字 |
| brainstorm G16 | 「手機只驗 ≤32」 | 逐字（★B-136 條文誤記為 G17） |
| `contracts/wire-user-admin.md` §3 | **守門序無此格**（形制→唯一→信箱格式→roleIds→N ⊆ A→政策→冷卻） | 逐字 |
| `contracts/msg-keys.md` | 二十個 `backend.biz.user.*` 鍵中**無**手機相關鍵 | 逐字 |
| DB `sys_user.user_phone` | `character varying`、**無長度上限**（`character_maximum_length` 為 NULL） | 2026-08-28 實測 |
| rev4 藍本 | `rev4:handler/user.rs`／`rev4:facade/sys_user.rs` 皆**無** phone 長度守門與對應 msg key | 逐字 |

⇒ 超長手機號**不會撞欄寬、不會 5000、不會被拒**，原樣落庫。

本刀 U2 落地 addUser 時發現這個缺格，**刻意沒有自行發明** `biz.user.userPhoneInvalid`——發明一個新的
業務拒因就是憑空造出一個使用者看得到的行為，且會讓 `msg-keys.md` 由 20 鍵變 21、連動 T051 的計數記載。
該單元把裁定立帳為 B-136 並標明「需 user 裁定」。

## 決定

**「≤32」是欄位的描述性上界，不是 MUST 守門。** 四個權威取「無守門」的那三個（契約守門序、msg-keys、
rev4 藍本），spec FR-008 與 brainstorm G16 的那個數字改讀為欄位語意說明。**碼零改動、零新拒因、
`msg-keys` 維持二十鍵。**

理由三條：

1. **三比一，且少數的那一個沒有來源。** 「32」這個數字在全 repo 找不到技術依據——DB 欄無上限、
   rev4 無守門、沒有任何下游消費者（簡訊閘道、匯出格式、對外 API）宣告過長度需求。它看起來像是
   寫 spec 時給欄位的一個直覺上界，而不是從約束推導出來的值。**為一個沒有來源的數字新增守門，
   等於把直覺固化成使用者可見的拒絕。**
2. **新增拒因的成本不對稱。** 補守門要動六處（契約守門序＋msg-keys＋兩語 locale＋`app.d.ts`＋
   handler＋測），而它擋掉的是一個**目前沒有人抱怨、也沒有下游會壞掉**的輸入；反過來，日後真的
   出現長度約束時再補，那時會有一個**真實的**上限值可寫，而不是 32。
3. **rev5 的既有取態一致。** 本刀在 `user_name` 上有形制守門（`^[A-Za-z0-9_-]{1,64}$`、自建）、
   在 `user_email` 上有簡式格式守門——兩者都有明確理由（帳號名是登入識別字、信箱要能寄信）。
   phone 沒有這樣的理由，而 rev5 不做「因為其他欄有守門所以這欄也該有」的對稱性推理。

## 替代案

**A. 補 `biz.user.userPhoneInvalid` 守門（B-136 選項①）。** 讓 spec FR-008 的字面被執行。未採——
理由見決定 1／2。★**它不是壞選項**：不設守門確實留下一個面（見後果），只是那個面的代價低於
新增拒因的代價，而且日後可逆（補守門隨時能做，撤掉一個已上線的拒因才難）。

**B. 維持現狀、不表態（B-136 選項③）。** 未採，且 B-136 條文自己就標了「不建議」——兩份權威留著
互相矛盾的真正代價是：**下一個讀 spec 的人以為守門存在、下一個讀契約的人以為不存在，而兩人都不會
發現對方的存在**。矛盾不會自己消失，只會在某次「為什麼這個值進得來」的排查裡浪費一輪。

## 後果

- `contracts/wire-user-admin.md` §3 的守門序**維持七格不變**；`msg-keys.md` 維持二十鍵；
  spec FR-008 就地補勘誤註指向本 ADR。B-136 關帳。
- ★**誠實記——不設守門留下的面**：使用者可以送出任意長度的手機字串並成功落庫。可見影響＝
  管理列表該欄會被撐開（`scroll-x` 是固定值、超長值會讓該儲存格換行或溢出），以及稽核 payload
  的 `audit_json` 快照會夾帶該長字串。**兩者都不造成資料損壞或安全問題**，且都是可回復的
  （改掉那筆資料即恢復）。
- ★**翻案觸發器**（明確、可檢驗）：出現**任何一個有來源的長度約束**時立即翻案並補守門——
  ①接上簡訊閘道且其 API 宣告號碼長度上限 ②手機欄進入對外 API 或匯出格式且該格式有欄寬
  ③法規或稽核要求號碼格式正規化。屆時上限值取**該來源宣告的值**，不是 32。
- ★**留給後人的判準**：欄位描述裡的數字要不要變成守門，先問「這個數字是從哪個約束推導出來的」——
  推導得出來就補守門（並在碼註寫明來源），推導不出來就是描述。**沒有來源的守門，擋掉的是使用者，
  保護的是沒有人。**
