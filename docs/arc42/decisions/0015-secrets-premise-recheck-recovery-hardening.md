## 背景

四反轉條件中「多人」已成立（.sops.yaml 兩把 age 公鑰、2026-08-06 首次真實加人已實跑），
「非工程師成員出現」的身分屬性 repo 無法判定、僅 user 能確認。原延後理由「單人工程師×
passphrase 僅存腦中×離線備份閉環」半邊失效，衍生兩個缺口：RUNBOOK §15.5 復原三情境表
全以「鑰失效」為前提、缺「成員離開／持鑰人失聯」列（完整程序在 §15.3 準則 1 有、復原表
未引用＝operator 入口斷）；兩把 identity 的 passphrase 皆僅存持鑰人腦中，雙人同失＝
密文永久不可解（§15.5 列三＝10 支機密全部重發）。

## 決定

- **子題一（主題）：前提未成立**——user 確認第二位持鑰人為工程師、無非工程師成員即將
  加入。四反轉條件**原樣過境本檔**、維持現行 SOPS 單層方案；「觸發即重啟選型、不是在
  現有方案上補 GUI」之約束句原樣過境。
- **子題二：§15.5 補列**——補「成員離開／持鑰人失聯」情境列，指向 §15.3 撤銷準則
  （只 re-key 不換值＝形式撤銷，撤銷必連帶輪替機密值本身）與 §15.6 輪替表。
  施工＝BACKLOG B-040（維護批第一支）。
- **子題三：先產第三把離線保管復原鑰**——不綁任何開發機、私鑰與 passphrase 離線保管，
  入 recipients＋updatekeys 回寫＋解回驗收；封掉「雙持鑰人同時失 passphrase」死路。
  施工＝BACKLOG B-041（維護批第一支）。

## 後果

- 重啟選型觸發器繼續活著：非工程師成員一旦出現即重啟**整個選型**（兩層設計＋橋接
  角色連同設計、獨立立案），不是補 GUI。
- 離線鑰入列後 recipient 2→3：§15.2 互動次數隨 recipient 數變動（L-005 已載）、
  RUNBOOK 對應處隨 B-041 施工同步；離線保管物納入離線備份義務範圍。
- 與 ADR 0014 交叉：prod 分層「不含開發機公鑰」要求本代不觸發；離線復原鑰是否充當
  該把，留待 prod 題重啟時定。
